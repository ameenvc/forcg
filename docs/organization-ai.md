# Organization-aware risk AI

The assistant can use an approved organization profile and source-linked knowledge when generating risk ideas, drafts, record reviews and register reviews. This is persistent organization context supplied with each live request; it does not fine-tune model weights. User feedback and AI answers do not automatically become facts.

## Activate after deployment

Apply only the new migration from the Laravel project directory:

```sh
php artisan migrate --path=database/migrations/2026_11_05_200000_create_risk_ai_organization_learning_tables.php --force
```

This targeted command avoids the repository's separate historical fresh-database migration ordering issue. The compatibility development helper offers `bash tools/risk-ai-dev.sh migrate-learning`. The migration was exercised against the local development MariaDB database; hosting has not been accessed.

Open **Organization AI** in the risk navigation. An administrator can manage it directly, or delegate **Organization AI knowledge** under Enterprise Risk in the existing module permission editor. The permission key is `manage-risk-ai-knowledge`; existing edit-all privileges do not automatically grant it.

Complete the organization name, industry, processes, locations, objectives, risk appetite, terminology and approved 3×3 criteria. Add a source/approval reference, enable context, and save. Each save appends an audited profile version. Disabling the latest profile disables all profile/note use; it never falls back to an older enabled version. Concurrent saves require the current revision.

Add approved notes with a source reference. Leave topics blank for general guidance or use comma-separated topic phrases for relevance matching. A review-by date excludes the note once that date has passed. Withdraw a note to stop future use while retaining its audit record.

Actual tailored generation requires the existing `RISK_AI_ENABLED=true`, `RISK_AI_MODE=openai`, configured server API key and model. Demo results remain labelled examples/checklists; storing an organization profile does not turn demo mode into live AI.

## Feedback loop

Generated answers show the approved profile version and relevant note sources supplied to the assistant. They also offer Helpful / Not relevant / Incorrect feedback. Corrections require a comment. The server resolves the referenced generated answer and verifies that it belongs to the signed-in actor and current organization namespace. Users cannot submit feedback against someone else's answer or an answer from another namespace.

Managers review feedback in Organization AI. They can acknowledge, dismiss, or publish a separately written, verified correction with a source reference. Publication creates approved knowledge and links it to the feedback. Neither the original AI answer nor the user's comment is promoted automatically. Only pending feedback can be processed, and a repeated review does not duplicate knowledge. Users see their own feedback; managers see the pending organization review queue.

Live record and register reviews can include `organization_comments`, rendered as Organization perspective. Existing deterministic scoring and human review/submission workflows remain unchanged. No risk records, ratings, owners or existing controls are updated by this learning workflow.

## Scope and retrieval

The current application uses one organization per installation/database. The server-owned `RISK_AI_ORGANIZATION_KEY` defaults to `installation` and is hashed for storage. It can be set to a stable, non-secret organization namespace before the first profile is created. Changing it selects separate memory; renaming the company in its profile does not change it. Requests cannot supply or override this key or the approved organization payload.

This is not a shared-database multi-tenant resolver. A deployment hosting multiple organizations in one database must wire an authoritative tenant context before using this feature across tenants. Existing risk records themselves have no tenant ID.

Retrieval considers the latest 100 approved, unexpired notes, selects matching topic phrases (including names/groups/areas in the register sample), and supplies at most five notes. General notes are eligible with lower relevance priority. The complete approved profile plus those notes are sent to the configured provider as untrusted background data, never as system instructions. The model is instructed to distinguish assumptions, cite only supplied note IDs, and avoid inventing controls or ratings. Source metadata in the response is generated by the server, not trusted from the model.

## Persistence and operations

Four tables store profile versions, approved/withdrawn notes, generated answers, and feedback. An answer audit stores a bounded topic (500 characters), validated response, actor identifier, action/mode, profile revision, selected note IDs and time. Full request prompts, risk descriptions and API credentials are not separately logged/stored as request logs; a generated answer may of course contain information supplied in its prompt. The application's generic SQL binding logger omits contents of these four tables. Normal application database access/retention controls apply; no automatic purge of memory or answer audit records is configured here.

Routes retain session authentication, MFA and CSRF for writes, with request throttling. Only administrators or explicitly delegated managers can modify shared context. Organization queries always use the server namespace. Template values and feedback render as escaped text; browser widgets do not create nested forms inside the risk-entry form.

Before the migration is installed, the workspace explains the one-time setup and generic risk AI continues without persistence or organization context. The feature never silently creates production tables or fabricated organization facts.

Validation covers role delegation, profile version conflicts/disablement, source requirements, approved/relevant/expired/withdrawn note selection, provider context injection and spoof rejection, feedback ownership and namespace isolation, duplicate submissions/reviews, approved promotion, escaped rendering, SQL-log redaction and migration-missing fallback. Browser checks cover the workspace, approval fields, contextual comments/sources, feedback submission, mobile layout and form/modal integration. Provider calls in tests are mocked; live provider responses and hosting deployment were not verified.
